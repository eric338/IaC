
```ini
[unreachable_hosts]
ansible-node9 ansible_host=192.168.56.199

[unreachable_hosts:vars]
ansible_ssh_common_args='-o ConnectTimeout=5 -o StrictHostKeyChecking=no'
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex07)
ansible nodes --list-hosts
```

**1-3.** `ansible-node1`에서 존재하지 않는 경로를 조회하는 명령을 `ignore_errors: true`로 무시하는 작업과, `ignore_unreachable`로는 이 실패를 막을 수 없다는 것을 확인하는 작업을 `ignore_errors_test.yml`에 작성하세요.

— `~/lab/ex07/ignore_errors_test.yml`
```yaml
---
- hosts: ansible-node1
  gather_facts: false

  tasks:
    - name: 존재하지 않는 경로 조회 (ignore_errors 로 무시)
      ansible.builtin.command: ls /no/such/path/ch07
      register: r1
      ignore_errors: true

    - name: r1 결과
      ansible.builtin.debug:
        msg: "failed={{ r1.failed }} rc={{ r1.rc }}"

    - name: 연결은 되지만 명령이 실패 (ignore_unreachable 로는 못 막는다)
      ansible.builtin.command: ls /no/such/path/ch07
      ignore_unreachable: true

    - name: 여기까지 오지 못한다
      ansible.builtin.debug:
        msg: "이 메시지는 출력되지 않는다"
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex07)
ansible-playbook ignore_errors_test.yml
```

(예상 출력)
```
TASK [존재하지 않는 경로 조회 (ignore_errors 로 무시)] ***
fatal: [ansible-node1]: FAILED! => {"changed": true, "cmd": ["ls", "/no/such/path/ch07"], "rc": 2, ...}
...ignoring

TASK [r1 결과] ***
ok: [ansible-node1] => {
    "msg": "failed=True rc=2"
}

TASK [연결은 되지만 명령이 실패 (ignore_unreachable 로는 못 막는다)] ***
fatal: [ansible-node1]: FAILED! => {"changed": true, "cmd": ["ls", "/no/such/path/ch07"], "rc": 2, ...}

PLAY RECAP ***
ansible-node1              : ok=2    changed=1    unreachable=0    failed=1    skipped=0    rescued=0    ignored=1
```

세 번째 작업은 SSH 연결에는 문제가 없고 명령 자체가 실패(`rc=2`)한 경우이므로 `ignore_unreachable`이 있어도 무시되지 않습니다. `ignore_unreachable`은 `UNREACHABLE` 상태만 무시하고 `FAILED` 상태는 무시하지 못하기 때문에 플레이가 여기서 중단되고, 마지막 `debug` 작업은 실행되지 않습니다.

**1-4.** `echo` 명령의 출력에 특정 문자열이 있는지로 `failed_when`을 재정의하는 작업과, 반환 코드가 0이어도 실패로 간주하는 작업을 `failed_when_test.yml`에 작성하세요.

— `~/lab/ex07/failed_when_test.yml`
```yaml
---
- hosts: ansible-node1
  gather_facts: false

  tasks:
    - name: 출력에 FAILED 문자열이 있으면 실패로 간주
      ansible.builtin.command: echo "backup completed OK"
      register: r1
      failed_when: "'FAILED' in r1.stdout"

    - name: r1 결과
      ansible.builtin.debug:
        msg: "failed={{ r1.failed }} stdout={{ r1.stdout }}"

    - name: 반환 코드가 0이어도 실패로 간주
      ansible.builtin.command: echo same
      register: r2
      failed_when: r2.rc == 0
      ignore_errors: true

    - name: r2 결과
      ansible.builtin.debug:
        msg: "rc={{ r2.rc }} failed={{ r2.failed }}"
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex07)
ansible-playbook failed_when_test.yml
```

(예상 출력)
```
TASK [출력에 FAILED 문자열이 있으면 실패로 간주] ***
changed: [ansible-node1]

TASK [r1 결과] ***
ok: [ansible-node1] => {
    "msg": "failed=False stdout=backup completed OK"
}

TASK [반환 코드가 0이어도 실패로 간주] ***
fatal: [ansible-node1]: FAILED! => {"changed": true, "cmd": ["echo", "same"], "failed_when_result": true, "rc": 0, "stdout": "same", ...}
...ignoring

TASK [r2 결과] ***
ok: [ansible-node1] => {
    "msg": "rc=0 failed=True"
}
```

첫 번째 작업은 출력에 `FAILED` 문자열이 없으므로 정상 `changed`로 끝납니다. 두 번째 작업은 명령의 **반환 코드는 0인데도** `failed_when: r2.rc == 0` 조건 때문에 실패로 처리되고, 결과에 `failed_when_result: true`가 함께 담깁니다.

**1-5.** `changed_when: false`를 조회 전용 명령에 붙이고, 조건부로 `changed`를 보고하는 작업을 `changed_when_test.yml`에 작성해 비교하세요.

— `~/lab/ex07/changed_when_test.yml`
```yaml
---
- hosts: ansible-node1
  gather_facts: false

  tasks:
    - name: 조회 전용 명령은 항상 changed 아님으로 보고
      ansible.builtin.command: cat /etc/hostname
      register: r1
      changed_when: false

    - name: r1 결과
      ansible.builtin.debug:
        msg: "changed={{ r1.changed }}"

    - name: 반환 코드가 2가 아니면 changed 로 보고
      ansible.builtin.command: echo river
      register: r2
      changed_when: "r2.rc != 2"

    - name: r2 결과
      ansible.builtin.debug:
        msg: "rc={{ r2.rc }} changed={{ r2.changed }}"
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex07)
ansible-playbook changed_when_test.yml
```

(예상 출력)
```
TASK [조회 전용 명령은 항상 changed 아님으로 보고] ***
ok: [ansible-node1]

TASK [r1 결과] ***
ok: [ansible-node1] => {
    "msg": "changed=False"
}

TASK [반환 코드가 2가 아니면 changed 로 보고] ***
changed: [ansible-node1]

TASK [r2 결과] ***
ok: [ansible-node1] => {
    "msg": "rc=0 changed=True"
}
```

`changed_when: false`가 붙은 첫 작업은 명령이 정상 실행되었어도 화면에 `ok`로만 표시됩니다. 반면 두 번째 작업은 `rc`가 0이라 `rc != 2` 조건이 참이 되어 `changed`로 보고됩니다. 조회 전용 `command`/`shell` 작업에서 불필요한 핸들러 트리거를 막을 때 이 패턴을 씁니다.

# 전략과 롤링 업데이트

**2-1.** `ansible-node1`만 4초 지연시키는 작업과 그다음 작업으로 구성된 플레이를 `linear`(기본) 전략과 `strategy: free` 전략 두 가지로 `strategy_compare.yml`에 작성해 비교하세요.

— `~/lab/ex07/strategy_compare.yml`
```yaml
---
- name: linear (기본)
  hosts: nodes
  gather_facts: false
  tasks:
    - name: node1 만 4초 지연
      ansible.builtin.command: sleep 4
      when: inventory_hostname == 'ansible-node1'
    - name: 두 번째 작업
      ansible.builtin.command: hostname

- name: free
  hosts: nodes
  strategy: free
  gather_facts: false
  tasks:
    - name: node1 만 4초 지연
      ansible.builtin.command: sleep 4
      when: inventory_hostname == 'ansible-node1'
    - name: 두 번째 작업
      ansible.builtin.command: hostname
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex07)
ansible-playbook strategy_compare.yml
```

(예상 출력) — 실제 타이밍(밀리초 단위)은 실행 환경마다 달라지므로 정확한 시각 대신 예상되는 실행 순서만 표시합니다.
```
PLAY [linear (기본)] ***

TASK [node1 만 4초 지연] ***
skipping: [ansible-node2]
changed: [ansible-node1]

TASK [두 번째 작업] ***
changed: [ansible-node1]
changed: [ansible-node2]

PLAY [free] ***

TASK [node1 만 4초 지연] ***
skipping: [ansible-node2]

TASK [두 번째 작업] ***
changed: [ansible-node2]

TASK [node1 만 4초 지연] ***
changed: [ansible-node1]

TASK [두 번째 작업] ***
changed: [ansible-node1]
```

`linear` 플레이는 `TASK` 헤더가 작업마다 한 번씩만 나오고, `ansible-node2`는 `ansible-node1`의 4초 지연이 끝난 뒤에야 두 번째 작업을 실행합니다(모든 호스트가 한 작업을 마쳐야 다음 작업으로 넘어가기 때문). `free` 플레이는 `ansible-node2`가 기다리지 않고 자신의 두 번째 작업을 먼저 끝내며, 호스트마다 진행 속도가 달라 `TASK` 헤더가 여러 번 반복해서 나타납니다.

**2-3.** `throttle: 1`을 특정 작업에 지정한 `throttle_test.yml`을 작성해, 두 호스트가 동시에 시작하지 않고 순차적으로 시작하는지 시작 시각을 찍어 확인하세요.

— `~/lab/ex07/throttle_test.yml`
```yaml
---
- hosts: nodes
  gather_facts: false

  tasks:
    - name: throttle 없음 - 두 호스트 동시 실행
      ansible.builtin.shell: "date +%H:%M:%S; sleep 4"
      register: a
    - name: 시작 시각 (throttle 없음)
      ansible.builtin.debug:
        msg: "{{ inventory_hostname }} 시작={{ a.stdout }}"

    - name: throttle 1 - 한 번에 한 호스트씩
      ansible.builtin.shell: "date +%H:%M:%S; sleep 4"
      throttle: 1
      register: b
    - name: 시작 시각 (throttle 1)
      ansible.builtin.debug:
        msg: "{{ inventory_hostname }} 시작={{ b.stdout }}"
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex07)
ansible-playbook throttle_test.yml
```

(예상 출력) — 정확한 초 단위 시각은 실행 시점마다 달라지므로 실제 값 대신 상대적인 차이의 패턴만 표시합니다. `throttle` 없이는 두 호스트의 시작 시각 차이가 거의 없어야(1초 안팎) 하고, `throttle: 1`에서는 앞 호스트의 작업 소요 시간(약 4초)만큼 차이가 나야 합니다.
```
TASK [시작 시각 (throttle 없음)] ***
    "msg": "ansible-node1 시작=<T>"
    "msg": "ansible-node2 시작=<T 와 거의 동일>"

TASK [시작 시각 (throttle 1)] ***
    "msg": "ansible-node1 시작=<T'>"
    "msg": "ansible-node2 시작=<T' + 약 4초>"
```

`throttle` 없음에서는 두 호스트가 동시에 작업을 시작하므로 시작 시각 차이가 거의 0에 가깝고, `throttle: 1`에서는 한 번에 한 호스트씩만 실행되므로 앞 호스트의 작업이 끝난 뒤에야 뒤 호스트가 시작해 시작 시각 차이가 작업 소요 시간만큼(여기서는 약 4초) 벌어집니다.

`ansible.cfg`에 값을 넣으면 출처가 `default`에서 파일 경로로 바뀌어 반영된 것을 확인할 수 있습니다.

```bash

ansible-config dump | grep -i forks
```

(예상 출력) — `-f`는 해당 실행 한 번에만 적용되는 임시 오버라이드이므로, `ansible-playbook` 실행에는 forks=10이 쓰이지만 실행이 끝난 뒤 `ansible-config dump`는 다시 `ansible.cfg`에 적힌 값(2)을 보여줄 것으로 예상됩니다.
```
DEFAULT_FORKS(~/lab/ex07/ansible.cfg) = 2
```

관리 노드가 2대뿐인 이 실습 환경에서는 `forks` 값이 2를 넘어가도 동시에 실행되는 호스트 수가 최대 2대라 체감되는 실행 결과 차이는 크지 않습니다. `forks`의 효과는 관리 대상이 많을수록 뚜렷해집니다.

**3-5.** `until`, `retries`, `delay`와 `async_status`를 조합해 4번의 비동기 작업이 끝날 때까지 기다렸다가 최종 결과(`rc`, `delta`)를 출력하는 작업을 추가해 `async_practice.yml`을 실행하세요.

— `~/lab/ex07/async_practice.yml` (3단계 — 이어서 작성)
```yaml
    - name: async_status 로 비동기 작업 완료를 기다림
      ansible.builtin.async_status:
        jid: "{{ sleeper.ansible_job_id }}"
      register: job_result
      until: job_result.finished
      retries: 4
      delay: 5

    - name: 최종 결과
      ansible.builtin.debug:

```

```bash

```

(예상 출력) — `sleep 20` 작업이 끝날 때까지 5초 간격으로 재시도하므로, 4번째 시도(약 20초 경과 시점) 전후로 완료될 것으로 예상됩니다. 정확히 몇 번째 시도에서 `finished: true`가 되는지는 타이밍에 따라 달라질 수 있습니다.
```
TASK [async_status 로 비동기 작업 완료를 기다림] ***
FAILED - RETRYING: [ansible-node1]: async_status 로 비동기 작업 완료를 기다림 (3 retries left).
FAILED - RETRYING: [ansible-node1]: async_status 로 비동기 작업 완료를 기다림 (2 retries left).
FAILED - RETRYING: [ansible-node1]: async_status 로 비동기 작업 완료를 기다림 (1 retries left).
changed: [ansible-node1]

ok: [ansible-node1] => {
    "msg": "finished=True rc=0 delta=0:00:20.0XXXXX"
}
```

`FAILED - RETRYING` 메시지는 오류가 아니라 `until` 조건(`job_result.finished`)이 아직 참이 아니어서 재시도한다는 뜻입니다.

완성된 `~/lab/ex07/async_practice.yml` 전체는 다음과 같습니다.

```yaml

  tasks:

      poll: 10

      poll: 0
      register: sleeper

    - name: 비동기 작업 사이에 다른 작업을 먼저 실행
      ansible.builtin.debug:
        msg: "비동기 작업이 도는 동안 이 작업이 먼저 끝난다 (job_id={{ sleeper.ansible_job_id }})"

    - name: async_status 로 비동기 작업 완료를 기다림
      ansible.builtin.async_status:
        jid: "{{ sleeper.ansible_job_id }}"
      register: job_result
      until: job_result.finished
      retries: 4
      delay: 5

    - name: 최종 결과
      ansible.builtin.debug:
        msg: "finished={{ job_result.finished }} rc={{ job_result.rc }} delta={{ job_result.delta }}"
```

# 작업 시작 및 단계

작업 디렉터리는 `~/lab/ex07`입니다. 4번 문제에서 작성한 `backup_tags.yml`을 그대로 사용합니다.

**5-1.** 앞 실습에서 만든 태그 플레이북(`backup_tags.yml`)을 `--start-at-task="Write log entry"`로 실행해, 앞의 작업들이 건너뛰어지는지 확인하세요(`always` 태그 작업도 건너뛰어지는 점에 주목하세요).

```bash
# ansible-ctrl에서 실행 (~/lab/ex07)
ansible-playbook backup_tags.yml --start-at-task="Write log entry"
```

(예상 출력)
```

    "msg": "log entry written"
}

PLAY RECAP ***
ansible-node1              : ok=1    changed=0    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
```

`Write log entry`보다 앞에 있는 작업은 모두 건너뜁니다. 특히 `Send notification`은 `always` 태그가 붙어 있어 `--tags`/`--skip-tags` 옵션만으로는 결코 건너뛸 수 없는 작업인데도, `--start-at-task`가 지정한 작업보다 앞이라는 이유만으로 함께 건너뛰어집니다. `always` 태그는 "태그로 실행 범위를 거를 때는 항상 포함한다"는 뜻이지, "시작 지점을 무시하고 무조건 실행한다"는 뜻이 아니기 때문입니다.


(예상 출력) — 대화형 세션이므로 실제로는 각 작업 실행 직전에 다음과 같은 프롬프트가 순서대로 나타날 것으로 예상됩니다.
```
Perform task: Take database backup (y/n/c):
```

- `y`를 입력하면 `Take database backup`이 실행되고, 다음 작업(`Verify backup integrity`)에 대한 프롬프트로 넘어갑니다.
- `n`을 입력하면 해당 작업을 건너뛰고 다음 작업 프롬프트로 넘어갑니다.
- `c`를 입력하면 이후로는 더 묻지 않고 남은 모든 작업을 순서대로 실행합니다.

**5-3.** `--list-tasks`로 확인했던 작업 이름 중 하나를 `--start-at-task`에 지정해 정확히 그 작업부터 시작하는지 확인하세요.

```bash
# ansible-ctrl에서 실행 (~/lab/ex07) — 4-5에서 확인한 목록 재사용
ansible-playbook backup_tags.yml --list-tasks
```

(예상 출력은 4-5의 `--list-tasks` 결과와 같습니다.)

```bash
# ansible-ctrl에서 실행 (~/lab/ex07)
ansible-playbook backup_tags.yml --start-at-task="Verify backup integrity"
```

(예상 출력)
```
TASK [Verify backup integrity] ***
ok: [ansible-node1] => {
    "msg": "backup integrity verified"
}

TASK [Send notification] ***
ok: [ansible-node1] => {
    "msg": "notification sent"
}

TASK [Write log entry] ***
ok: [ansible-node1] => {
    "msg": "log entry written"
}
```

`--list-tasks`로 확인한 이름을 그대로 지정하면 정확히 그 작업부터 시작하고, 이후 작업은 순서대로 이어서 실행됩니다. `Take database backup`은 지정한 작업보다 앞이므로 건너뜁니다.

**5-4.** 이름이 없는 작업에는 `--start-at-task`를 쓸 수 없다는 것을 직접 시도해 확인하세요(또는 이유를 정리해 보세요).

— `~/lab/ex07/noname_test.yml`
```yaml
---
- hosts: ansible-node1
  gather_facts: false

  tasks:
    - ansible.builtin.debug:
        msg: "이름 없는 작업"

    - name: 이름 있는 작업
      ansible.builtin.debug:
        msg: "이름 있음"
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex07)
ansible-playbook noname_test.yml --list-tasks
```

(예상 출력) — 이름이 없는 작업은 모듈명(및 인자)을 그대로 붙여 자동 생성한 이름으로 표시될 것으로 예상됩니다.
```
playbook: noname_test.yml

  play #1 (ansible-node1): ansible-node1	TAGS: []
    tasks:
      ansible.builtin.debug	TAGS: []
      이름 있는 작업	TAGS: []
```

`--start-at-task`는 정확한 작업 이름 문자열을 그대로 지정해야 동작합니다. 이름이 없는 작업은 `--list-tasks`에 표시되는 값 자체가 모듈명(때로는 인자 일부)을 기반으로 자동 생성된 것이라 플레이북을 조금만 고쳐도 표시 이름이 달라질 수 있고, 애초에 사용자가 의도적으로 붙인 식별자가 아니므로 `--start-at-task`의 안정적인 지정 대상으로 쓰기 어렵습니다. 이런 문제를 피하려면 모든 작업에 고유하고 의미 있는 `name`을 붙이는 것이 안전합니다.
