# 정적 인벤토리와 그룹 구성

1. `~/lab/ex03` 디렉터리를 만들고, `ansible.cfg`에 `inventory = ~/lab/inventory.ini`를 등록하세요. 이후 `ansible all --list-hosts`로 실습 랩의 전체 호스트가 몇 대인지 확인하세요.
2. `mail.example.com`, `192.168.56.51`을 그룹 없이, `webservers`(foo, bar), `dbservers`(one, two, three)를 그룹으로 나눈 정적 인벤토리를 `group_inventory.ini`에 INI 형식으로 작성하고, `ansible-inventory --graph`로 `ungrouped`에 어떤 호스트가 들어가는지 확인하세요.
3. `group_inventory.ini`에 `east`, `west` 그룹을 추가하고, `prod`가 `east`와, `test`가 `west`와 같은 호스트를 갖도록 각 호스트를 다시 나열한 `duplicated_inventory.ini`를 작성하세요. 이어서 `[prod:children]`, `[test:children]`을 사용해 중복을 제거한 `nested_inventory.ini`를 작성하고, 두 파일의 `--graph` 결과가 어떻게 다르게 표시되는지 비교하세요.
4. 호스트 범위 표기(`www[01:05].example.com`)와 스트라이드(`www[01:07:2].example.com`), 알파벳 범위(`db-[a:c].example.com`)를 각각 그룹으로 담은 `range_inventory.ini`를 작성하고, `--graph`로 실제 몇 개의 호스트로 펼쳐지는지 확인하세요.
5. `nested_inventory.ini`에 대해 `ansible-inventory --list`(JSON 전체 출력)와 `ansible-inventory --host foo.example.com`(개별 호스트 변수 출력)을 각각 실행하고, 두 출력이 서로 어떤 정보를 보여주는지 비교하세요.

# 패턴을 이용한 대상 선택

1. `~/lab/inventory.ini`를 대상으로 `all`, `control`, `nodes`, `broken` 각 패턴에 `--list-hosts`를 실행해 몇 대씩 걸리는지 확인하세요.
2. `all:!broken` 패턴으로 `broken` 그룹을 제외한 호스트만 나오는지 확인하고, 이런 제외 패턴이 실무에서 왜 유용한지 생각해 보세요(예: 아직 준비되지 않은 노드를 잘못 건드리지 않기 위함).
3. `webservers`(foo, bar), `dbservers`(one, two), `east`(foo, one), `west`(bar, two)가 겹치도록 구성한 `pattern_inventory.ini`를 작성하고, 합집합(`:`), 교집합(`:&`), 제외(`:!`) 패턴을 각각 `--list-hosts`로 실행해 결과를 비교하세요.
4. 3번 인벤토리에 대해 `webservers:dbservers:&east:!west` 같은 혼합 패턴을 실행하고, 어떤 순서로 계산되어 그 결과가 나왔는지 설명하세요.
5. `pattern_inventory.ini`에 와일드카드 패턴(`*.example.com`)을 실행해 보고, 이어서 호스트 이름이 `web`, `db`로 시작하는 것만 걸러내는 정규 표현식 인벤토리(`regex_inventory.ini`)와 패턴(`~(web|db).*`)을 작성해 실행하세요. 패턴을 따옴표 없이 실행하면 어떤 문제가 생기는지도 확인하세요.

# 구성 파일 탐색 순서와 제어 우선순위

1. `~/lab/ex03/cfgtest/nocfg` 디렉터리를 만들고 그 안에서 `ansible --version`의 `config file` 줄과 `ansible-config dump | grep DEFAULT_HOST_LIST`를 실행해, 구성 파일이 하나도 없을 때 어떤 기본값이 적용되는지 확인하세요.
2. `~/lab/ex03/cfgtest/ansible.cfg`에 `inventory = ~/lab/inventory.ini`, `forks = 17`, `remote_user = vagrant`를 지정하고, 그 디렉터리에서 다시 `ansible --version`을 실행해 `config file` 값이 바뀌는지 확인하세요.
3. `forks = 42`만 정의한 `env-ansible.cfg`를 같은 디렉터리에 만들고, `ANSIBLE_CONFIG` 환경 변수로 지정해 `ansible-config dump --only-changed`를 실행하세요. `remote_user` 설정이 결과에 나타나는지 확인하고, 이것이 두 구성 파일이 병합되지 않는다는 증거임을 설명하세요.
4. `cfgtest/ansible.cfg`가 적용되는 디렉터리에서, 옵션 없이 `whoami`를 실행했을 때, 존재하지 않는 사용자를 `-u`로 지정했을 때, 그리고 `-e ansible_user=vagrant`를 추가로 지정했을 때 세 가지 경우의 결과를 각각 실행해 비교하고, 구성 파일 · 명령줄 옵션 · `-e` 변수의 우선순위를 정리하세요.
5. `ansible-config list`로 `DEFAULT_HOST_LIST` 항목의 상세 정보(환경 변수 이름, INI 섹션과 키 이름)를 조회하세요.

# 관리 노드 연결과 권한 상승

1. `~/lab/ex03`에서 `ssh-keygen -lf ~/.ssh/id_ed25519.pub`로 제어 노드의 SSH 키 지문을 확인하고, `ssh-keygen -F ansible-node1`로 `ansible-node1`의 호스트 키가 `known_hosts`에 등록되어 있는지 확인하세요.
2. `host_key_checking`의 기본값을 `ansible-config dump | grep HOST_KEY_CHECKING`으로 확인하고, `ANSIBLE_HOST_KEY_CHECKING=false`를 명령 앞에 붙였을 때 같은 조회 결과가 어떻게 달라지는지 확인하세요. `ansible.cfg`를 직접 고치지 않고 환경 변수로 그 명령에 한해서만 적용하는 이유도 설명하세요.
3. `ansible-node1`을 대상으로 존재하지 않는 사용자(`ch03_nouser`)를 `-u`로 지정해 `ansible.builtin.ping`을 실행하고 어떤 오류가 나는지 확인한 뒤, `-u` 없이 다시 실행해 정상 동작함을 확인하세요.
4. `nodes` 그룹을 대상으로 `-b` 옵션 없이, 그리고 `-b` 옵션(또는 `-e ansible_become=true`)을 붙여서 각각 `whoami`를 실행하고 결과가 어떻게 달라지는지 비교하세요.
5. `ansible-ctrl`을 대상으로 기본 `ssh` 연결과 `-c local` 연결로 각각 `hostname`을 실행해 보고, 두 방식의 차이와 `local` 연결이 유용한 상황을 설명하세요.
