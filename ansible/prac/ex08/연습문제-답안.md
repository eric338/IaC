**1-4.** `include_vars` 모듈로 `site_settings.yml`을 축약형으로, `queue_vars.yml`은 `name: cfg`를 지정해 각각 가져오는 작업을 `includevars.yml`에 작성해 `cfg.queue_name` 형태로 참조해 보세요.

**1-5.** 같은 파일에 `include_vars`를 `when` 조건 뒤에 붙인 작업을 추가해, 조건이 거짓일 때는 파일을 읽지 않는다는 것을 확인하세요.

— `~/lab/ex08/includevars.yml`
```yaml
---
- name: include_vars 모듈로 변수 파일 가져오기
  hosts: localhost
  gather_facts: false
  tasks:
    - name: site_settings.yml 을 축약형으로 가져오기 (최상위 변수)
      ansible.builtin.include_vars: site_settings.yml

    - name: queue_vars.yml 을 cfg 변수 아래로 가져오기
      ansible.builtin.include_vars:
        file: queue_vars.yml
        name: cfg

    - name: 결과 확인
      ansible.builtin.debug:
        msg: "banner_text={{ banner_text }} http_port={{ http_port }} cfg.queue_name={{ cfg.queue_name }} cfg.queue_user={{ cfg.queue_user }}"

    # 1-5. include_vars 는 작업(task)이므로 when 조건을 걸 수 있다.
    # run_conditional_include 는 어디서도 true 로 정의하지 않았으므로 이 작업은 항상 skip 된다.
    - name: 조건이 거짓이면 queue_vars.yml 을 최상위 변수로는 읽지 않음
      ansible.builtin.include_vars: queue_vars.yml
      when: run_conditional_include | default(false)

    - name: 조건부 include_vars 결과 확인 (최상위 queue_name 은 정의되지 않아야 함)
      ansible.builtin.debug:
        msg: "queue_name(top-level)={{ queue_name | default('정의되지 않음 (조건이 거짓이라 파일을 읽지 않음)') }}"

    # 1-6. vars_files 는 플레이 수준 키워드로, 플레이가 파싱/시작되는 시점에 무조건 읽힌다.
    # when 같은 조건과 결합할 수 없다. 반대로 include_vars 는 작업(task)이므로 when, loop 와
    # 자유롭게 결합할 수 있다.
    # 결론: 파일을 "조건에 따라서만" 읽어야 한다면 vars_files 가 아니라 include_vars 를 써야 한다.
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex08)
ansible-playbook includevars.yml
```

(실행 결과 — 로컬 재현 확인) `name`을 지정한 `cfg`는 `cfg.queue_name` 형태로, 지정하지 않은 `site_settings.yml`은 `banner_text`처럼 최상위 변수로 바로 접근한다. `when` 조건이 거짓인 작업은 `skipping`으로 표시되고, 그 결과 최상위 `queue_name` 변수는 정의되지 않은 채로 남는다.
```
TASK [site_settings.yml 을 축약형으로 가져오기 (최상위 변수)] **************************
ok: [localhost]

TASK [queue_vars.yml 을 cfg 변수 아래로 가져오기] ***************************************
ok: [localhost]

TASK [결과 확인] ********************************************************************
ok: [localhost] => {
    "msg": "banner_text=Ex08 사이트 배너 http_port=8080 cfg.queue_name=order-queue cfg.queue_user=queueuser"
}

TASK [조건이 거짓이면 queue_vars.yml 을 최상위 변수로는 읽지 않음] **************************
skipping: [localhost]

TASK [조건부 include_vars 결과 확인 (최상위 queue_name 은 정의되지 않아야 함)] ***************
ok: [localhost] => {
    "msg": "queue_name(top-level)=정의되지 않음 (조건이 거짓이라 파일을 읽지 않음)"
}

PLAY RECAP *************************************************************************
localhost                  : ok=4    changed=0    unreachable=0    failed=0    skipped=1    rescued=0    ignored=0
```

**1-6.** `vars_files`와 `include_vars` 중 "조건부로만 읽어야 하는 경우"에 어느 쪽을 써야 하는지 결론을 코드 주석으로 남기세요.

→ 위 `includevars.yml` 하단의 주석에 결론을 남겼다. `vars_files`는 플레이 수준 키워드로 플레이 시작 시 무조건 읽히므로 `when`을 걸 수 없고, `include_vars`는 작업(task)이므로 `when`·`loop`와 자유롭게 결합할 수 있다. 따라서 조건부로만 읽어야 하는 경우에는 `include_vars`를 써야 한다.

작업 디렉터리는 다시 `~/lab/ex08`입니다(문제 1의 1-2에서 만든 `ansible.cfg`를 그대로 씁니다). 이 절의 예제는 모두 `hosts: localhost`로 작성해 인벤토리 내용과 무관하게 동작을 확인합니다.

```yaml

- name: include_tasks 로 helpers 가져오기 (동적)
  hosts: localhost

  tasks:
    - name: start
      ansible.builtin.debug:
        msg: start

    - name: Include helpers
      ansible.builtin.include_tasks: helpers.yaml

    - name: end
      ansible.builtin.debug:
        msg: end
```

```yaml
---
- name: import_tasks 로 helpers 가져오기 (정적)
  hosts: localhost

  tasks:
    - name: start
      ansible.builtin.debug:
        msg: start

    - name: Import helpers
      ansible.builtin.import_tasks: helpers.yaml

    - name: end
      ansible.builtin.debug:
        msg: end
```


두 플레이북 모두 실행하면 `start` → `stepA` → `stepB` → `end` 순서로 debug 메시지가 출력된다는 점에서는 동일하다. 차이는 다음 3-2에서 `--list-tasks`로 확인한다.

**3-2.** 두 플레이북에 `--list-tasks`를 실행해 내부 작업이 보이는지 여부를 비교하세요.

```bash

```

(실행 결과 — 로컬 재현 확인) `include_tasks`는 실행 시점에 동적으로 작업을 추가하므로, 파싱만 하는 `--list-tasks`에는 `helpers.yaml` 내부의 `stepA`/`stepB`가 보이지 않고 `Include helpers`라는 모듈 작업 이름만 보인다(08.md 8.2.3의 `dynamic.yml` 예제와 동일한 원리).

**3-3.** `salute.yaml`(`item` 인사)을 `include_tasks` + `loop`로 반복 실행하는 `dynamic_loop.yml`을 작성해 실행해 보고, 같은 것을 `import_tasks` + `loop`로 바꾼 `static_loop.yml`을 실행해 오류가 나는지 확인하세요.

— `~/lab/ex08/salute.yaml`
```yaml
- name: 인사
```

```yaml
- name: include_tasks 를 반복문과 함께 사용
```

**3-4.** 내부 작업에 태그를 붙인 파일(`sectioned.yaml`)을 각각 `include_tasks`(`tag_dynamic.yml`) / `import_tasks`(`tag_static.yml`)로 가져와 `--tags`로 내부 작업만 선택할 수 있는지 비교하세요.

```yaml
- name: inner_a
  ansible.builtin.debug:

  tags: [alpha]

- name: inner_b
  ansible.builtin.debug:
    msg: inner_b
  tags: [beta]
```

— `~/lab/ex08/tag_dynamic.yml`
```yaml

  gather_facts: false
```

```yaml

  gather_facts: false

      ansible.builtin.import_tasks: sectioned.yaml

```

**3-5.** 4번의 두 플레이북에 각각 `--start-at-task`로 정적/동적 방식에서 내부 작업까지 시작 지점으로 지정할 수 있는지 비교하세요.

```bash
# ansible-ctrl에서 실행 (~/lab/ex08)
ansible-playbook tag_dynamic.yml --start-at-task inner_a
```

(실행 결과 — 로컬 재현 확인) `--start-at-task`는 정적으로 펼쳐진 작업 목록에서만 시작 지점을 찾을 수 있다. `include_tasks`로 가져온 `inner_a`는 파싱 시점에는 존재하지 않는(실행 시점에야 나타나는) 작업이므로 찾지 못하고 오류가 난다(08.md `dynamic.yml --start-at-task task3` 예제와 동일한 원리).
```
PLAY [include_tasks 와 태그] ********************************************************

PLAY RECAP **************************************************************************

[ERROR]: No matching task "inner_a" found. Note: --start-at-task can only follow static includes.
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex08)
ansible-playbook tag_static.yml --start-at-task inner_b
```

(실행 결과 — 로컬 재현 확인) `import_tasks`로 가져온 `inner_a`, `inner_b`는 파싱 시점에 이미 정적인 작업 목록의 일부이므로, `inner_b`부터 정상적으로 시작한다(08.md `static.yml --start-at-task task3` 예제와 동일한 원리).
```
PLAY [import_tasks 와 태그] *********************************************************

TASK [inner_b] ***********************************************************************
ok: [localhost] => {
    "msg": "inner_b"
}

PLAY RECAP **************************************************************************
localhost                  : ok=1    changed=0    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
```

**요약**: `include_tasks`(동적)는 실행 시점에 작업을 추가하므로 `--list-tasks`에 내부 작업이 보이지 않고, 내부 작업의 태그로 `--tags`를 걸 수 없으며, `--start-at-task`로 내부 작업을 시작 지점으로 지정할 수 없다. 반면 `import_tasks`(정적)는 파싱 시점에 내부 작업이 그대로 펼쳐지므로 `--list-tasks`에 보이고, `--tags`·`--start-at-task` 모두 내부 작업 이름으로 그대로 사용할 수 있다. `loop`는 정반대로 동적 방식(`include_tasks`)에서만 쓸 수 있고, 정적 방식(`import_tasks`)에서는 파싱 오류가 난다.
