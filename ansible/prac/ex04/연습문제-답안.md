**1-2.** 부울 값 다섯 가지 표기(`yes`, `no`, `True`, `TRUE`, `false`)를 변수로 정의하고 `ansible.builtin.debug`로 출력하는 작업을 `yaml_bool.yml`에 작성해 `nodes` 그룹에 실행하고, 다섯 표기가 모두 `True`/`False` 두 값으로만 해석되는지 확인하세요.

— `~/lab/ex04/yaml_bool.yml`
```yaml
---
- name: Boolean spellings
  hosts: nodes
  gather_facts: false
  vars:
    create_key: yes
    needs_agent: no
    knows_oop: True
    likes_emacs: TRUE
    uses_cvs: false
  tasks:
    - name: Print booleans
      ansible.builtin.debug:
        msg: "{{ create_key }} {{ needs_agent }} {{ knows_oop }} {{ likes_emacs }} {{ uses_cvs }}"
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex04)
ansible-playbook yaml_bool.yml
```

```
(예상 출력)
TASK [Print booleans] ***********************************************************
ok: [ansible-node1] => {
    "msg": "True False True True False"
}
ok: [ansible-node2] => {
    "msg": "True False True True False"
}
```

4.1.5절에서 확인한 대로 `yes`/`True`/`TRUE`는 모두 `True`로, `no`는 `False`로 해석되어 결과적으로 두 값(`True`/`False`)으로만 수렴합니다.

**1-3.** `windows_drive: c:`처럼 콜론 뒤에 값이 오는 잘못된 표기를 `yaml_colon_bad.yml`에 작성해 `--syntax-check`로 오류가 나는지 확인하고, 작은따옴표로 감싸 고친 `yaml_colon_fixed.yml`을 작성해 문제없이 통과하는지 비교하세요.

— `~/lab/ex04/yaml_colon_bad.yml`
```yaml
---
- name: Colon trap (broken)
  hosts: nodes
  gather_facts: false
  vars:
    windows_drive: c:
  tasks:
    - name: Print drive
      ansible.builtin.debug:
        var: windows_drive
```

`c:` 뒤에 아무 값도 없이 콜론이 하나 더 나타나는 형태로 해석되어(4.1.8.1절), 사전 값 안에 구분자로 쓰인 `:`과 충돌합니다. 정확한 오류 문구는 Ansible 버전에 따라 다를 수 있습니다.

```yaml

  hosts: nodes
  gather_facts: false
  vars:
    windows_drive: 'c:'
  tasks:
    - name: Print drive

        var: windows_drive
```



값 전체를 작은따옴표로 감싸면 콜론이 문자열의 일부로 인식되어 구문 오류가 사라집니다.

**1-4.** `foo: "{{ variable }}/additional/string/literal"`처럼 사전 값 전체를 큰따옴표로 감싸 변수와 리터럴 문자열을 함께 쓰는 올바른 예제를 `yaml_var_quote.yml`에 작성하고, 값의 일부만 인용해 구문 오류가 나는 형태는 주석으로 함께 남겨 두 형태를 비교하세요.

— `~/lab/ex04/yaml_var_quote.yml`
```yaml
---
- name: Variable quoting
  hosts: nodes
  gather_facts: false
  vars:
    variable: "opt"
  tasks:
    # 잘못된 형태(구문 오류) - 값의 일부만 인용:
    #   foo: "E:\\path\\"rest\\of\\path
    - name: 올바른 형태 - 값 전체를 인용
      ansible.builtin.debug:
        msg: "{{ variable }}/additional/string/literal"
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex04)
ansible-playbook yaml_var_quote.yml
```

```
(예상 출력)
TASK [올바른 형태 - 값 전체를 인용] ***********************************************
ok: [ansible-node1] => {
    "msg": "opt/additional/string/literal"
}
ok: [ansible-node2] => {
    "msg": "opt/additional/string/literal"
}
```

값의 일부만 인용하는 잘못된 형태(`"E:\\path\\"rest\\of\\path`)는 큰따옴표가 중간에서 닫혀 버려 뒤에 남은 텍스트가 YAML 파서 입장에서 해석 불가능한 토큰이 되므로 `--syntax-check` 단계에서 바로 실패합니다(4.1.8.2절). 그래서 실제 파일에는 남기지 않고 주석으로만 대조합니다.

**1-5.** `non_boolean: "yes"`, `version: "1.0"`처럼 부울/부동소수점으로 해석될 값을 따옴표로 강제로 문자열화하는 예제를 `yaml_string_force.yml`에 작성하고, 따옴표를 없앤 경우와 `ansible.builtin.debug` 출력이 어떻게 달라지는지 비교하세요.

— `~/lab/ex04/yaml_string_force.yml`
```yaml
---
- name: Force string type
  hosts: ansible-node1
  gather_facts: false
  vars:
    non_boolean: "yes"
    other_string: "False"
    version_quoted: "1.0"
    version_unquoted: 1.0
  tasks:
    - name: Show quoted values (strings)
      ansible.builtin.debug:
        msg: "non_boolean={{ non_boolean }} ({{ non_boolean | type_debug }}), version_quoted={{ version_quoted }} ({{ version_quoted | type_debug }})"

    - name: Show unquoted value (float)
      ansible.builtin.debug:
        msg: "version_unquoted={{ version_unquoted }} ({{ version_unquoted | type_debug }})"
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex04)
ansible-playbook yaml_string_force.yml
```

```
(예상 출력)
TASK [Show quoted values (strings)] *********************************************
ok: [ansible-node1] => {
    "msg": "non_boolean=yes (str), version_quoted=1.0 (str)"
}

TASK [Show unquoted value (float)] **********************************************
ok: [ansible-node1] => {
    "msg": "version_unquoted=1.0 (float)"
}
```

따옴표로 감싼 `"yes"`, `"1.0"`은 각각 부울/부동소수점으로 해석되지 않고 문자열(`str`) 타입을 유지합니다. 따옴표 없는 `1.0`은 실수(`float`)로 해석되므로, 특정 버전 문자열처럼 항상 문자 그대로 취급해야 하는 값은 반드시 따옴표로 감싸야 합니다(4.1.8.3절).

# 플레이북 작성과 멱등성

작업 디렉터리는 `~/lab/ex04`입니다(문제 1의 1-1에서 만든 `ansible.cfg`를 그대로 씁니다).

**2-1.** 이미 작성되어 있는 `install_cowsay.yml`을 열어 `hosts`, `become`, `tasks` 키와 두 작업이 각각 어떤 모듈을 호출하는지 확인한 뒤 `nodes` 그룹을 대상으로 실행하세요.

— `~/lab/ex04/install_cowsay.yml` (기존 파일, 수정하지 않고 그대로 사용)
```yaml
---
- name: Install cowsay on managed nodes
  hosts: nodes
  become: true

  tasks:
    - name: Ensure cowsay is installed
      ansible.builtin.apt:
        name: cowsay
        state: present
        update_cache: true

    - name: Deploy a marker file
      ansible.builtin.copy:
        dest: /etc/ex04-marker.txt
        content: "managed by ansible\n"
        owner: root
        group: root
        mode: '0644'
```

- `hosts: nodes`: 인벤토리의 `nodes` 그룹(ansible-node1, ansible-node2)을 대상으로 합니다.
- `become: true`: 패키지 설치와 `/etc` 아래 파일 생성에 root 권한이 필요하므로 권한을 상승시킵니다.
- 첫 번째 작업은 `ansible.builtin.apt` 모듈로 `cowsay` 패키지를 설치하고, 두 번째 작업은 `ansible.builtin.copy` 모듈로 `/etc/ex04-marker.txt` 파일을 배포합니다.

```bash
# ansible-ctrl에서 실행 (~/lab/ex04)
ansible-playbook install_cowsay.yml
```

**2-2.** 처음 실행한 결과의 PLAY RECAP에서 `changed` 값이 몇인지 확인하세요.

```
(예상 출력)

ok: [ansible-node1]
ok: [ansible-node2]

TASK [Ensure cowsay is installed] ***********************************************

```

패키지가 아직 설치되어 있지 않고 마커 파일도 없던 첫 실행이므로, 두 작업 모두 `changed`로 보고되어 `changed=2`가 됩니다.

**2-3.** `install_cowsay.yml`을 다시 한번 그대로 실행해, 이번에는 모든 작업이 `changed` 없이 `ok`로만 보고되는 것을 확인하고 그 이유를 멱등성 개념으로 설명하세요.

```bash
# ansible-ctrl에서 실행 (~/lab/ex04)
ansible-playbook install_cowsay.yml
```

```
(예상 출력)
TASK [Ensure cowsay is installed] ***********************************************
ok: [ansible-node1]
ok: [ansible-node2]

TASK [Deploy a marker file] ******************************************************
ok: [ansible-node1]
ok: [ansible-node2]

PLAY RECAP ***********************************************************************
ansible-node1              : ok=3    changed=0    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
ansible-node2              : ok=3    changed=0    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
```

`ansible.builtin.apt`와 `ansible.builtin.copy` 모두 "원하는 최종 상태가 이미 달성되었는가"를 먼저 확인하는 멱등적 모듈입니다(4.2.4절). `cowsay`는 이미 설치되어 있고 마커 파일 내용도 이미 일치하므로 실제로 아무 것도 바꾸지 않고 `ok`만 보고합니다. `changed`는 "명령을 실행했는가"가 아니라 "관리 노드의 상태가 바뀌었는가"를 뜻하므로, 플레이북을 몇 번이든 안심하고 다시 실행할 수 있습니다.

**2-4.** `ansible.builtin.command`로 `date` 명령을 실행하는 작업을 `idempotence_break.yml`에 작성해 `nodes` 그룹에 두 번 연달아 실행하고, `install_cowsay.yml`의 cowsay 설치 작업과 달리 매번 `changed`로 보고되는 이유를 설명하세요.

— `~/lab/ex04/idempotence_break.yml`
```yaml
---
- name: Non-idempotent command example
  hosts: nodes
  gather_facts: false
  tasks:
    - name: Run date command
      ansible.builtin.command: date
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex04)
ansible-playbook idempotence_break.yml
ansible-playbook idempotence_break.yml
```

```
(예상 출력, 두 번의 실행 모두 동일)
TASK [Run date command] *********************************************************
changed: [ansible-node1]
changed: [ansible-node2]

PLAY RECAP ***********************************************************************
ansible-node1              : ok=1    changed=1    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
ansible-node2              : ok=1    changed=1    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
```

`ansible.builtin.command`(그리고 `ansible.builtin.shell`, `ansible.builtin.raw`)은 4.2.4절에서 언급한 대로 멱등성을 제공하지 않는 대표적인 모듈입니다. 이 모듈은 "원하는 최종 상태"라는 개념 자체가 없이 명령을 실행한 사실만 알고 있으므로, 별도로 `changed_when`을 지정하지 않으면 실행할 때마다 무조건 `changed`로 보고합니다.

**2-5.** `ansible nodes -b -m ansible.builtin.apt -a "name=cowsay state=absent"` ad-hoc 명령으로 cowsay를 제거한 뒤 `install_cowsay.yml`을 다시 실행해, cowsay 설치 작업만 `changed`로 나오고 마커 파일 배포 작업은 `ok`로 유지되는지 확인하세요.

```bash
# ansible-ctrl에서 실행 (~/lab/ex04)
ansible nodes -b -m ansible.builtin.apt -a "name=cowsay state=absent"
ansible-playbook install_cowsay.yml
```

```
(예상 출력)
TASK [Ensure cowsay is installed] ***********************************************
changed: [ansible-node1]
changed: [ansible-node2]

TASK [Deploy a marker file] ******************************************************
ok: [ansible-node1]
ok: [ansible-node2]

PLAY RECAP ***********************************************************************
ansible-node1              : ok=3    changed=1    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
ansible-node2              : ok=3    changed=1    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
```

ad-hoc 명령으로 관리 노드의 실제 상태(cowsay 제거)만 바꿔 놓았으므로, 플레이북을 다시 실행하면 상태가 어긋난 cowsay 설치 작업만 `changed`로 원상복구되고, 이미 원하는 내용과 일치하는 마커 파일 작업은 `ok`를 유지합니다. 각 작업의 멱등성이 서로 독립적으로 평가된다는 것을 보여 줍니다.

# 체크 모드와 차이점 모드

작업 디렉터리는 `~/lab/ex04`입니다. 문제 2에서 `install_cowsay.yml`을 이미 한 번 이상 실행해 두었다고 가정합니다.

**4-1.** `install_cowsay.yml`을 이미 한 번 실행해 둔 상태에서 `--check`로 실행해, 실제 변경 없이 `changed=0`으로 시뮬레이션되는지 확인하세요.

**4-2.** `ansible nodes -b -m ansible.builtin.apt -a "name=cowsay state=absent"`로 cowsay를 제거한 뒤 `--check` 모드로만 `install_cowsay.yml`을 실행해 보고, 실제로 cowsay가 설치되었는지 확인해 체크 모드가 "실제 실행 결과의 예측"이 아니라는 것을 검증하세요.

`--check`는 관리 노드를 실제로 바꾸지 않으므로, 체크 모드에서 `changed`로 표시되었더라도 제거된 cowsay는 여전히 설치되어 있지 않습니다. 4.3.3절의 주의사항처럼 체크 모드는 "현재 상태 기준의 시뮬레이션"일 뿐, 실제 실행 결과를 보장하지 않습니다. (이 랩에서는 `update_cache: true`가 이미 여러 번 실제로 수행된 뒤라 apt 캐시가 최신 상태이므로, 4.3.3절 본문의 예제와 달리 패키지를 찾지 못해 실패하는 상황까지는 재현되지 않을 수 있습니다. 실제 결과는 랩 환경의 apt 캐시 상태에 따라 달라질 수 있습니다.)

# Ansible Lint

작업 디렉터리는 `~/lab/ex04`입니다. `ansible-lint`는 4.3.7.1절에서 안내한 대로 `pipx install ansible-lint`로 미리 설치되어 있다고 가정합니다.

**5-1.** 대문자로 시작하지 않는 플레이/작업 이름과 `yes`, `True` 같은 부울 표기를 일부러 사용한 `lint_practice.yml`을 작성하고 `ansible-lint`로 검사해 `name[casing]`, `yaml[truthy]` 위반이 각각 몇 건 나오는지 확인하세요.

— `~/lab/ex04/lint_practice.yml`
```yaml
---
- name: lint practice playbook
  hosts: nodes
  gather_facts: false
  vars:
    debug_enabled: yes
    strict_mode: True
  tasks:
    - name: print a flag
      ansible.builtin.debug:
        msg: "{{ debug_enabled }} {{ strict_mode }}"
```

```bash
# ansible-ctrl에서 실행 (~/lab/ex04)
ansible-lint lint_practice.yml
```

플레이 이름(`lint practice playbook`)과 작업 이름(`print a flag`)이 소문자로 시작해 `name[casing]` 위반이 2건, `yes`/`True` 표기가 `yaml[truthy]` 위반 2건으로 각각 보고됩니다. 정확한 건수와 규칙 프로파일은 `ansible-lint` 버전에 따라 달라질 수 있습니다.

**5-3.** YAML 문법 함정 주제의 2번 문제에서 만든 `yaml_bool.yml`을 `ansible-lint`로 검사해 `yaml[truthy]` 위반 건수를 확인하고, 4.1.5절 `bool_test.yml` 예제의 결과와 비교하세요.
